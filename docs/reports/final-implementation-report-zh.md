## 1. 随手记实操调研

### 1.1 方法
- 使用 Chrome DevTools 操作真实的 `https://www.feidee.com/cloud/#/`，所用会话是你已经登录的账号。
- 新建合成测试账本 `BW合成测试-勿用`，所有新建、修改、删除测试都只在这个账本中进行。
- 另建了一个 `BW合成测试-删除` 账本，专门用来测试“删除账本”。
- **你原有的 4 个账本（past (1)、past (2)、Dark time Mum、lulu life）没有打开过**，账本列表截图里只露出了它们的名称和封面。
- 没有付费，没有上传任何文件，也没有邀请任何人。

### 1.2 主要发现（全部是亲手操作后得出的）

- **账户**
  - 共 7 种类型，各类型的表单字段完全相同。
  - 期初余额和修改余额都会生成一条差额流水：资产账户叫“余额变更”，负债账户叫“负债变更”。
  - 网页版的信用卡表单没有额度、账单日、还款日。
  - **删除账户会连同它的全部流水一起删除**，包括转账，因此对方账户的余额也会跟着变化。
- **分类**
  - 两级结构，二级分类可以换父级、可以隐藏。
  - **删除分类会连同它的流水一起删除**，不能迁移。
- **转账**
  - 一条记录同时带转出和转入两个账户。
  - 跨币种转账保存两个金额，并自动按汇率折算成人民币。
- **信用卡还款**：就是一笔转入信用卡的转账，会减少负债。
- **退款**：保存为分类里的一笔负数支出，备注预填“#退款#”，**不关联原始消费**。
- **网页版没有的功能**：预算、周期记账、借贷中心、回收站、操作日志查看、封账、结转、对账、账户和分类排序。
- **付费功能**：
  - 新建商家：Pro
  - 数据导出：Basic
  - 记多笔：Basic
  - 自定义首页：Basic

## 3. 本次实现

### 3.1 共享领域模型（finance-core，两端共用）
- `packages/finance-core/schema/financial-schema.json` 是唯一的数据源，Rails 和 TypeScript 都读取它。内容包括：
  - 账户类型及其资产/负债属性
  - 8 种流水类型（kind）
  - 关联类型
  - 类型推断规则
  - 去重规则
- `src/ledger/domain.ts` 包含：类型推断、余额、净资产、总额、录入校验、周期日期、预算周期。
- `src/ledger/dedupe.ts` 实现行级去重。
- `src/ledger/organize.ts` 生成 AI 整理建议，是纯函数，不修改任何数据。
- 契约用例同时在 Vitest 和 Minitest 中运行：
  - `kind-cases.json`
  - `dedupe-cases.json`
  - `ledger/appendix2-scenario.json`

### 3.2 P0 五项关键修复

| 问题 | 解决方案 | 测试 |
|---|---|---|
| ① 跨账号数据隔离 | 服务器新增不可变的 `users.finance_owner_uid`，接口返回 `owner_id`。每个本地数据库记录 `owner_account_id`，每个账号有自己的数据库列表。其他账号的数据库不会被打开、下载写入、上报或删除。升级后第一个登录的账号接管旧列表；在这个列表之外发现无主但有数据的库时，会询问“这是你的数据库吗？”。服务器较旧、还没有 `owner_id` 时，先用邮箱哈希绑定，之后自动升级为 id。 | `ownerBinding.test.tsx`（两个账号共用同一设备）、`account.test.ts` |
| ② 收入统计错误 | 流水有明确的 `kind`。收入 = kind 为 income 的合计；支出 = expense 与 refund 的净额。退款冲减所在分类，信用卡还款和转账不计入收支。导入时按账户类型推断，信用卡上的入账不会算作收入。旧数据按原规则回填（各项合计不变），疑似退款/还款的进入“需检查的收入”列表，由你确认后再改。 | 两端均有测试，网页端另做了浏览器实测：收入 $0，支出 $50 |
| ③ 跨文件重复导入 | 网页端新增 `Finance::DuplicateDetector`，按账户依次比对银行参考号、“日期+金额+描述”（带出现次数计数）和近似匹配：完全重复的自动跳过，可疑的进入“可能重复”列表。本地端修复了无账户旧行被当成通配符的问题（R9）。 | `dedupe-cases.json`、`duplicate_import_test.rb` |
| ④ 保留银行原文 | 新增 `original_description` 列，回填自原描述。网页端用 `attr_readonly` 保护，本地用 SQLite 触发器禁止修改。编辑时只改显示描述；对于导入的流水，金额和日期作为证据保持不变。 | `migration0007.test.ts`、`ledger-store.test.ts` |
| ⑤ 本地备份与恢复 | (1) Rust 端在每次迁移前，自动按字节复制每个槽位文件（含 -wal/-shm），每个槽位保留最近 2 份，可在“数据管理”中把副本打开为新数据库。(2) 用户手动备份：导出完整的逻辑副本和校验信息，可选 AES-GCM 口令加密，只保存到你选择的文件。(3) 恢复：**只写入新的空槽位**，写完后逐表核对行数和金额合计，任何不一致都会清空新槽位、整体回滚，原数据库不受影响。 | Rust 测试 15 项（含快照 4 项）、`backup.test.ts`（含加密、篡改、回滚） |

`local-db-backups-20261113/` 里的真实备份**没有打开或修改**，测试只用了合成数据库。

### 3.3 手动记账（两端均已实现，不依赖 AI）
- **账户**
  - 9 种类型，支持期初余额、信用卡额度/账单日/还款日、计入净资产开关、备注。
  - 可归档、恢复、排序、调整余额（生成余额调整流水）。
  - 有流水的账户只能归档，不能删除。
- **记一笔**
  - 类型：支出、收入、转账（转入负债账户时自动视为还款）、退款（选择原始消费，可部分退款，超额会被拒绝）、余额调整。
  - 字段：日期、时间、商家、项目、标签、备注、描述。
- **流水管理**：编辑、复制、删除到回收站、恢复、彻底删除、批量修改（分类/商家/项目/标签）和批量删除，可按类型、账户、维度筛选。
- **分类**
  - 两级结构，收入树和支出树分开，可隐藏、排序。
  - 删除时可选择流水迁移到哪个分类；也可以合并分类。
  - 自定义分类上限从 50 提高到 200。
- **商家、项目、标签**：新建、重命名、合并、归档、删除。删除时只清空流水上的这个字段，流水本身保留。
- **预算**：按月或按年；可针对全部支出、某个分类或某个项目；达到 90% 时提醒；支持自定义月起始日。
- **周期记账**：可预览下几期日期；补记到期流水（同一期不会重复）；可跳过一期、暂停；可选择在打开 App 时自动记账。
- **报表**：按分类、账户、商家、项目、标签或月份统计；净资产按月变化。
- **操作日志**：每一次修改都会记录是谁或什么做的（你、导入、规则、AI、周期记账），以及修改前后的值。

### 3.4 AI 一键整理（本地端已实现）
- 流程：分析 → 预览 → 勾选 → 应用 → 撤销。
- 能识别的情况：
  - 未分类流水
  - 自己账户之间的转账
  - 信用卡还款
  - 可匹配原始消费的退款
  - 重复流水
  - 被误计为收入的流水
  - 商家名整理
  - 周期性支出（只作为提示，不会自动创建）
- 默认完全在设备上用规则计算，不联网。可选的云端分类沿用已有的同意机制，只发送清洗后的商家名和收付方向。
- 应用时使用与手动操作相同的账本操作，作为一个批次写入日志，可以整批撤销。**你锁定过的字段永远不会被改动。**

## 4. 数据库变更

### 4.1 PostgreSQL
4 个迁移，全部只增不删：
- `20261115000100_add_finance_owner_uid_to_users`
- `20261115000200_add_ledger_columns_to_finance_transactions`
  - 新增 uuid、kind、original_description、账户、来源、软删除等字段
  - `statement_id` 允许为空，但有 CHECK 约束：只有手动流水和周期流水可以为空
- `20261115000300_extend_finance_bank_accounts`：新增账户类型、期初余额、信用卡字段、归档等
- `20261115000400_create_finance_ledger_tables`：新建 books、links、audit_events、merchants、projects、tags、transaction_tags、budgets、recurring_rules、category_settings、organize_runs

### 4.2 SQLite
新增迁移 `0007_ledger.sql`，同样只增不删，没有重建任何表：
- 新增 accounts、links、维度、预算、周期规则、日志、organize_runs 等表。
- 新增四类触发器：
  - 保证每条流水都有 uuid 和银行原文
  - 禁止修改银行原文
  - 用单条语句原子地写入转账两腿和关联
  - 对退款金额设上限
- 回填 kind（按原规则，所有合计不变）、账户（来自 account_key；未知账户归入“导入（无账户）”）、期初余额（来自对账单期末余额，标记为“估算”）。
- 为避免高风险的表重建，手动流水挂在每个账本一条隐藏的“手动流水容器”对账单上（`source_format='manual'`）。

### 4.3 迁移顺序
备份/快照 → 新增结构 → 回填（保持现有合计不变）→ 校验 → 切换读写 → 验证。没有删除任何旧结构：`finance_custom_categories` 和文本 `category` 列都保留了。

## 6. 未完成项与风险

1. **网页端 AI 整理界面未实现**：只有数据表和日志里的批次撤销，分析和预览界面目前只在本地端有。
2. **网页端多账本界面未实现**：已有 `finance_books` 和默认账本，但没有切换和新建界面。本地上传到网页后，目前仍进入默认账本（K.2 Q7）。
3. **未实现**：多币种和汇率、附件图片、记多笔、借贷中心和联系人、账户级对账界面、成员和角色（FinRx）。
4. **原生 App 没有实际启动验证**：Tauri 原生构建没有打包运行。快照逻辑由 Rust 单元测试覆盖，备份恢复由 sql.js 覆盖，iOS/Android 实机行为未验证。
5. **pooled 连接导致的原子性限制**：本地插件使用连接池，因此“修改”和“写日志”是两条语句。极端情况（崩溃）下，可能出现修改成功但日志缺失。转账、退款和导入已经用触发器保证原子。
6. **生产上线前**：需要先建 Neon 分支、再执行 4 个迁移、验证合计不变，然后同时发布网页和 App（App 需要 `owner_id`）。本次**没有执行**任何生产迁移。
7. **其他**：开发环境的 `.env.local` 指向 Neon 的 `production` 分支。本次所有 Rails 命令都显式设置了本地 `DATABASE_URL`。建议把开发环境改为独立的 Neon 分支。

## 7. 与随手记的刻意差异

| 方面 | 随手记 | BillieWeather | 原因 |
|---|---|---|---|
| 删除分类或账户 | 连同流水一起删除 | 迁移流水或只能归档 | 不静默丢失历史（I-9） |
| 删除流水 | 立即删除，网页版没有回收站 | 软删除，进回收站，可恢复 | 可恢复、可审计 |
| 退款 | 负数支出，不关联原消费 | 关联原消费，有部分退款上限 | 统计更准，防止超额退款 |
| 转账 | 一条记录 | 两腿加关联 | 每条银行明细独立成行，更适合导入和去重（评审方案 C） |
| 商家、导出 | 付费 | 免费 | 产品定位 |
| 结转、封账、角色 | 有 | 暂不做 | 保持历史连续；角色留给 FinRx |

K.2 的十个待决问题，每项的备选方案、默认选择、随手记依据、数据库影响、体验影响和依赖关系，见 `finance-domain-spec.md` 第 8 节。
